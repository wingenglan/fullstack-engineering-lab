### 1. docker-compose.yml 中的环境变量语法

**问题**：`MYSQL_DATABASE: ${MYSQL_DATABASE:-engineering_lab}` 是什么意思？

**解答**：这是 Shell 变量替换语法。
- 读取环境变量 `MYSQL_DATABASE`
- 如果该变量**未设置或为空**，则使用 `engineering_lab` 作为默认值
- Docker Compose 启动时会**自动读取当前目录下的 `.env` 文件**加载环境变量

相关语法：
| 语法 | 含义 |
|---|---|
| `${VAR:-default}` | 变量未设置或为空时用 default |
| `${VAR-default}` | 变量未设置时用 default（空字符串不算） |
| `${VAR:?error msg}` | 变量未设置时报错退出 |

### 2. cp 命令和 make 命令

**问题**：`cp .env.example .env` 和 `make up` 是什么？

**解答**：
- `cp` 是 Linux/macOS 的文件复制命令，Windows 对应 `copy`
- `make` 是构建工具，读取当前目录的 `Makefile` 文件执行任务
- `make up` 实际执行的是：`docker compose -f deploy/docker-compose.yml --env-file .env up -d`
- Windows 下需要安装 make：`choco install make`（需管理员权限）或直接运行 Makefile 里的实际命令

### 3. deploy 目录下的配置文件

**问题**：`deploy/nginx/nginx.conf`、`deploy/mysql/init.sql`、`deploy/redis/redis.conf` 各自的作用？

**解答**：
| 文件 | 作用 | 加载时机 |

### 4. Nginx 核心配置速查

**问题**：Nginx 快速入门需要掌握哪些配置？

**解答**：

```nginx
# 路由规则 — 最核心
location /api/ {
    proxy_pass http://server;          # 转发给后端
    proxy_set_header X-Real-IP $remote_addr;  # 传递客户端真实 IP
}

# upstream 定义后端服务地址
upstream server {
    server server:8080;    # 容器服务名:端口
}
```

| 配置 | 含义 |
|---|---|
| `listen 80` | 监听端口 |
| `location /path` | URL 路径匹配 |
| `proxy_pass` | 反向代理转发 |
| `upstream` | 定义后端服务地址 |
| `gzip on` | 开启响应压缩 |

**proxy_pass 末尾斜杠的区别**：
- `proxy_pass http://docs/;`（有斜杠）→ 去掉 location 匹配的前缀
- `proxy_pass http://docs;`（无斜杠）→ 原样转发

### 5. Docker 内部网络与端口

**问题**：为什么 `upstream web { server web:80; }` 和 `upstream docs { server docs:80; }` 都是 80 端口，不冲突吗？

**解答**：不冲突。每个 Docker 容器有**独立的网络空间**，容器内的端口互相隔离。

```
容器 web   → 172.18.0.3:80  （自己的 IP）
容器 docs  → 172.18.0.4:80  （自己的 IP）
```

Docker 内部 DNS 把**服务名**解析成对应容器 IP。`server web:80` 中的 `web` 是 docker-compose 的**服务名**（不是 container_name），在 Docker 网络中充当域名。

宿主机端口才不能重复，所以 docker-compose.yml 里每个服务映射到宿主机的端口都不同。

### 6. Go 后端 Dockerfile 两阶段构建

**问题**：为什么 Dockerfile 分两个阶段？为什么要 COPY configs 和 docs 目录？

**解答**：

```dockerfile
# 第一阶段：编译（golang 镜像，~300MB）
FROM golang:1.21-alpine AS builder
RUN go build -o server ./cmd/server/

# 第二阶段：运行（alpine 镜像，~5MB）
FROM alpine:3.18
COPY --from=builder /app/server .         # 编译出的二进制
COPY --from=builder /app/configs ./configs # 配置文件（运行时读取）
COPY --from=builder /app/docs ./docs       # Swagger 文档（运行时提供）
```

- Go 编译后是独立二进制，不需要编译器
- `configs/` 和 `docs/` 不是代码的一部分，不会被编译进二进制，是程序运行时从磁盘读取的
- 两阶段构建的目的是让最终镜像尽可能小（只包含二进制 + 运行时需要的文件）

### 7. Viper 配置加载机制

**问题**：`config.go` 中的 `Load` 函数如何加载配置？如何指定运行环境？

**解答**：配置加载分三层，优先级从低到高：

```
config.yaml（基础配置）
    ↓ 被覆盖
config.dev.yaml 或 config.prod.yaml（环境配置）
    ↓ 被覆盖
环境变量（Docker 注入，优先级最高）
```

**核心代码解析**：
```go
v.AutomaticEnv()    // 自动读取操作系统环境变量
v.SetEnvKeyReplacer(strings.NewReplacer(".", "_"))  // yaml key 的 "." 替换成环境变量的 "_"
```

转换过程（**两步**）：
```
yaml key        replacer 转换     viper 自动大写      匹配环境变量
"app.env"   →   "app_env"    →    "APP_ENV"      →   查找 APP_ENV
"mysql.host" →  "mysql_host" →    "MYSQL_HOST"   →   查找 MYSQL_HOST
```

- 第①步：`SetEnvKeyReplacer` 把点号换成下划线
- 第②步：`AutomaticEnv()` **自动**把 key 转成大写（内置行为，不需要配置）

**指定运行环境**：docker-compose.yml 通过环境变量 `APP_ENV: prod` 控制，viper 会自动读取并加载对应的 `config.prod.yaml`。

### 8. Context 机制

**问题**：`context.WithTimeout` 返回的两个值是什么？怎么用？

**解答**：

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()    // 函数结束时立即释放资源
```

| 返回值 | 类型 | 作用 |
|---|---|---|
| `ctx` | `context.Context` | 带有5秒倒计时的上下文，传给下游操作 |
| `cancel` | `func()` | 手动取消的函数，提前结束计时器 |

**自定义函数使用 ctx**：
```go
func doWork(ctx context.Context) {
    for i := 1; i <= 10; i++ {
        select {
        case <-ctx.Done():   // ctx 被取消了？
            fmt.Println("被取消:", ctx.Err())
            return
        default:             // 还没取消，继续干活
            fmt.Println("处理第", i, "步")
            time.Sleep(1 * time.Second)
        }
    }
}
```

`ctx.Done()` 返回一个 channel，ctx 过期或被 cancel 时会收到信号。

**为什么中间件用 `c.Request.Context()`？**
因为它是当前 HTTP 请求自带的 context，客户端断开连接时会自动取消，避免资源浪费。

### 9. Gin 中间件与 Abort

**问题**：中间件中 `c.Next()` 和 `c.Abort()` 的区别？

**解答**：
- `c.Next()` — 放行，继续执行后面的 handler（执行完后会回来执行后续代码）
- `c.Abort()` — 立即终止，不再往后执行

```go
// JWT 中间件示例
authHeader := c.GetHeader("Authorization")
if authHeader == "" {
    response.Error(c, ...)
    c.Abort()    // 终止！不放行
    return
}
// ... 更多检查 ...
c.Next()         // 全部通过，放行
```

### 10. HTTP 服务的优雅关闭

**问题**：为什么 `ListenAndServe` 要放在 goroutine 里？优雅关闭是怎么实现的？

**解答**：

```go
go func() {
    srv.ListenAndServe()   // 阻塞的，必须放 goroutine 里
}()

quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)  // 监听 Ctrl+C 和 docker stop
<-quit   // 阻塞等待信号

srv.Shutdown(shutdownCtx)  // 停止接受新请求，等待旧请求完成（最多10秒）
```

- goroutine 里运行服务，main 协程继续往下等信号
- `Shutdown` 做三件事：停止接受新请求 → 等待正在处理的请求完成 → 超时强制关闭

### 11. Redis 在项目中的用途（JWT 黑名单）

**问题**：Redis 在这个项目里是干嘛的？

**解答**：只用于**登出后的 token 黑名单**。

JWT token 有效期 2 小时，用户退出后 token 仍然有效。解决方案：

```go
// 登出时：把 token 存入 Redis 黑名单，设过期时间 = token 剩余有效期
rdb.Set(ctx, "blacklist:"+token, "1", 2*time.Hour)

// 中间件验证时：先查 Redis 黑名单
exists, _ := rdb.Exists(ctx, "blacklist:"+token).Result()
if exists > 0 {
    // token 已作废，拒绝请求
}
```

Redis 就是超快的键值数据库，这里只用了两个操作：
- `SET key value TTL` — 登出时写入黑名单
- `EXISTS key` — 鉴权时检查是否在黑名单

### 12. VitePress 文档服务部署踩坑

**问题**：VitePress 文档服务部署到 Docker 后出现各种问题。

**踩坑记录**：

| 问题 | 原因 | 解决 |
|---|---|---|
| 看到 Nginx 默认欢迎页 | Nginx 自带的 `index.html` 没被删除 | Dockerfile 中 `RUN rm -rf /usr/share/nginx/html/*` |
| 样式巨丑，只有纯文本 | CSS 文件返回 `Content-Type: text/html` | nginx 配置加 `include /etc/nginx/mime.types;` |
| 资源文件 404 | VitePress 的 `assets/` 在根目录，不在 `docs/` 子目录 | 用 `alias` 或调整目录结构 |
| 刷新后闪烁然后 404 | VitePress 客户端路由 hashmap key 不匹配 | 设置 `srcDir: 'docs'` 消除 key 前缀差异 |
| `alias` + `try_files` 兜底失效 | nginx 的 `alias` 和 `try_files` 配合有 bug | 改用 `rewrite ^/docs/(.*)$ /$1 last;` |

**最终 VitePress 配置**：
```ts
export default defineConfig({
  base: '/docs/',       // 所有资源路径加 /docs/ 前缀
  srcDir: 'docs',       // 源文件在 docs/ 子目录（消除 hashmap key 前缀）
  cleanUrls: false,     // 链接带 .html 后缀
})
```

**最终 nginx 配置**（docs 容器内）：
```nginx
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;
    include /etc/nginx/mime.types;
    location /docs/ {
        rewrite ^/docs/(.*)$ /$1 last;   # 去掉 /docs/ 前缀
    }
    location / {
        try_files $uri $uri/ /index.html; # 找文件，找不到返回首页
    }
}
```

**外部 nginx 代理**（不剥离前缀）：
```nginx
location /docs/ {
    proxy_pass http://docs;   # 无尾部斜杠，保留 /docs/ 前缀
}
```

### 13. Go 后端分层架构

**四层架构**：
```
handler（接待员）→ service（业务员）→ repository（仓库管理员）→ MySQL/Redis
```

| 层 | 职责 | 示例 |
|---|---|---|
| handler | 接收请求，解析参数，返回响应 | `ShouldBindJSON` → 调用 service → `response.Success` |
| service | 业务逻辑 | 查重、密码校验、JWT 生成、登出黑名单 |
| repository | 数据库 CRUD | `gorm.Where().First()`、`db.Create()` |
| model | 数据结构 | 数据库表结构（User）、请求/响应结构（DTO） |

**路由一览**：
```
/api/v1/
├── GET  /health           ← 公开
├── POST /auth/register    ← 公开
├── POST /auth/login       ← 公开
├── GET  /auth/profile     ← 需要 JWT
└── POST /auth/logout      ← 需要 JWT
```

### 14. 请求完整流向

```
浏览器 → localhost:8888
    → 宿主机端口映射 → Docker 容器 nginx:80
        → Nginx 根据 URL 分发：
            /api/*        → Go 后端 (server:8080)
            /docs/*       → VitePress 文档 (docs:80)
            /swagger/*    → Go 后端 (server:8080)
            /* 其他       → Vue 前端 (web:80)
        → Go 后端需要数据库？→ Docker 内部网络访问 mysql:3306
        → Go 后端需要缓存？→ Docker 内部网络访问 redis:6379
    → 响应原路返回
```

**关键点**：
- 只有 Nginx 一个入口（8888 端口），这是**网关模式**
- Docker 内部网络中，**服务名就是域名**（容器名不一定是）
- MySQL/Redis 只在内部网络通信，不直接暴露给浏览器

## 2026-06-15 — Redis 分布式锁案例开发与学习

---

### 1. 分布式锁解决什么问题？

单机程序可以用 `sync.Mutex`（互斥锁）保护共享资源，但**多台服务器部署时**，各自的锁互不认识，互斥失效。

**解决方案**：用 Redis 作为所有服务器都能访问的"公共裁判"，实现跨进程、跨机器的互斥。

```
单机锁：每台服务器各有一把锁 → 互不感知
分布式锁：所有服务器去 Redis 借同一把锁 → 全局互斥
```

---

### 2. Redis SET NX EX 命令

分布式锁的加锁命令：

```redis
SET lock:order:10086 "a1b2c3d4-..." NX EX 10
```

| 部分 | 含义 | 大白话 |
|------|------|--------|
| `SET key value` | 把值存到 key | "我要占这个位置" |
| `NX` | Not eXists，key 不存在才设置 | "如果没人占，我才占" |
| `EX 10` | 10 秒后自动过期 | "就算忘了还，10 秒后自动还" |

三个组合：**互斥（NX）+ 防死锁（EX）+ 持有者标识（value）**

Go 代码对应：
```go
ok, err := l.rdb.SetNX(ctx, l.key, l.value, l.ttl).Result()
// ok=true 抢到锁  ok=false 被别人占了
```

---

### 3. 释放锁为什么用 Lua 脚本？

**错误做法**：直接 `DEL key` → 可能误删别人的锁（自己的锁过期后被别人获取了）

**正确做法**：先比较 value 是否是自己的，再删除。但"比较+删除"必须是**原子操作**（不能被打断），所以用 Lua 脚本：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])    -- 是我的，删
else
    return 0                              -- 不是我的，不动
end
```

Go 代码：
```go
script := redis.NewScript(`...`)
result, err := script.Run(ctx, l.rdb, []string{l.key}, l.value).Int64()
```

- `KEYS[1]` → 锁的 Redis key
- `ARGV[1]` → 持有者标识（随机 token）
- Redis 保证脚本执行期间不被打断

**锁的安全三道防线**：SET NX（互斥）+ Lua（安全释放）+ EX（防死锁）

### 4. Lock 结构体设计

```go
type Lock struct {
    rdb    *redis.Client   // Redis 客户端
    key    string          // 锁名，如 "lock:order:10086"
    value  string          // 随机生成的持有者标识（每次不同）
    ttl    time.Duration   // 过期时间
    locked bool            // 是否持有锁
}
```

| 方法 | Redis 操作 | 作用 |
|------|-----------|------|
| `New()` | — | 创建锁实例，还没加锁 |
| `Acquire()` | `SET NX EX` | 尝试加锁 |
| `Release()` | Lua 脚本 `GET+DEL` | 原子释放锁 |
| `GetLockInfo()` | `GET` + `TTL` | 查询锁状态 |

### 5. Go 并发基础（用于并发争抢演示）

**协程（goroutine）**：`go func() { ... }()` 启动一个并发任务，"你去干你的，我不等你"

**互斥锁（sync.Mutex）**：保护共享数据不被多个协程同时写入

```go
mu.Lock()
results[id] = xxx    // 同一时刻只有一个协程能执行这里
mu.Unlock()
```

**等待组（sync.WaitGroup）**：等所有协程完成再继续

```go
wg.Add(1)         // 计数器 +1
go func() {
    defer wg.Done()   // 结束时 -1
    // ... 干活 ...
}()
wg.Wait()         // 阻塞，直到计数器归零
```

### 6. 并发争抢演示的执行流程

```
5 个协程同时 SET NX 同一个 key：

协程1  ──SET NX──→ 成功！→ 业务处理500ms → 释放锁 → 记录成功
协程2  ──SET NX──→ 失败（key已存在）→ 记录失败，结束
协程3  ──SET NX──→ 失败 → 记录失败，结束
协程4  ──SET NX──→ 失败 → 记录失败，结束
协程5  ──SET NX──→ 失败 → 记录失败，结束

结果：1 成功，4 失败 → 直观展示分布式锁的互斥特性
```
